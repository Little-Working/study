# 六种 SSR 框架无压缩、无 HTML ETag 复测方法

本轮是独立实验。工作负载改为真实的大 JSON，并关闭测试请求路径上的 gzip/br 与 ETag。不得把新旧结果直接相除后解释成某一项优化的收益；旧实验同时存在数据结构、页面构成、监控、压测器和服务入口差异。

## 请求实际做了什么

每次访问都经过 `HTTP 请求 → 框架 loader/server function → 真实 HTTP 后端 → 完整 JSON 读取与解析 → 原生组件遍历 → HTML 渲染与 hydration 数据序列化 → 压测器完整收完响应`。

三种页面均显示 Hello World。中页使用 800 条商品，大页使用 1,536 条商品；每条都有 id、标题、独立描述与价格。六种框架的组件结构、静态属性和数据相同，保留各自原生 SSR、数据传递与 hydration 格式，不使用预拼接 HTML，也不关闭 hydration 来提高分数。Next.js 使用 App Router 与服务端渲染的 Client Component；SolidJS 使用 SolidStart。

本轮字段是平面商品记录与 ASCII 文本。深层嵌套、富类型、大量转义字符或多字节文本可能改变解析与序列化成本，本轮不覆盖这些数据形状。

后端在启动时生成不可变 JSON 模板，中页精确 320,000 字节，大页精确 600,000 字节，KB 按十进制计。每次请求替换等长的 20 字符请求标识，等待指定时间后通过 HTTP 传输完整 JSON。数据并非供前端自行扩展的简短描述符。模板预序列化用于压低 mock 后端开销；本实验不测 mock 后端每次 `JSON.stringify` 的成本。应用每次仍须读取、解析全量 JSON，并由框架序列化 hydration 数据。

后端延迟分为固定 50、200、500 ms 三档，不是每次随机延迟。计时器实际等待时间另有记录；它可能因调度而略高于设定值。后端 CPU、GC、事件循环和调用数也被采集，用于检查后端瓶颈及缓存绕过。

## 关闭附加计算的方式

- Next.js：`compress:false`、`generateEtags:false`，动态页面且 fetch 禁用缓存。
- React Router：使用已安装的官方 Express adapter 启动 production build，`app.disable('etag')`；入口不挂载压缩中间件或访问日志。该入口只服务本次 HTML 工作负载。
- SvelteKit：adapter-node 不预压缩；在 production 产物中精确删除 HTML `hash(transformed)` 所在的 ETag 计算语句。补丁断言匹配数为 1，记录前后 SHA-256。仅删响应头无法省去哈希成本，因此这里改的是计算点。**这是用于隔离 ETag 成本的受控补丁，不代表 SvelteKit 默认配置的表现。**
- Nuxt：禁用路由缓存及 public assets 预压缩；TanStack Start、SolidStart 不添加压缩或 SSR 缓存中间件。

有效范围是本次动态 HTML 与 mock API 请求链路。构建文件名中的内容哈希、未请求的静态资源 ETag 元数据不属于本次请求计算；本实验也不测静态资源服务性能。

每个框架验收 36 次：3 页面 × 3 延迟 × 2 Accept-Encoding（identity 与 gzip/deflate/br）× 2 次相同 URL。检查状态 200、无 ETag/Content-Encoding、行数、首末商品、请求标识、结束标志及响应字节数；重复 URL 必须仍然一进一出访问后端。验收期间额外预加载探针：zlib 压缩入口、npm etag 入口或 Node ETag 设置被调用即报错。正式压测不加载这些重型验收探针。配置、源码补丁、主动协商和运行时探针共同提供证据，不能只凭响应头缺失断言省去了计算。

独立阳性测试确认 16 个压缩入口、ESM 压缩绑定、npm/Next ETag 函数和响应头探针会在主动调用时触发，结果保存在 `evidence/sentinel-selftest.json`；该测试在 builder 中执行，不计入服务压测。探针不是对所有内部哈希函数的全面追踪，其结论仍需结合配置和生成产物源码阅读。

## 隔离与顺序

使用同一固定摘要 Node Docker 镜像和 ARM64 架构，所有依赖通过保留的 lockfile 执行 `npm ci`，所有应用执行 production build。每个时刻只运行一个被测框架，后端和压测器独立容器。

| 角色 | Linux 虚拟 CPU 集 | CPU 配额 | 内存上限 |
|---|---|---:|---:|
| SSR 应用 | 0–1 | 2 CPU | 1,536 MiB；V8 old space 1,024 MiB |
| 压测器 | 2–5 | 4 CPU | 1 GiB |
| mock 后端 | 6–7 | 2 CPU | 512 MiB |

这是 OrbStack 虚拟机内的 CPU 隔离，不是宿主机物理核心独占，也不证明完全排除了宿主机其他应用、功耗和温度变化。Node 单进程不会因配额为 2 自动变成两个 SSR worker。

## 预先确定的测量安排

客户端与监控两类开销对照都采用大页、后端 50 ms、并发 64；不代表其他负载点具有相同的开销比例。低负载 CPU ms/请求还可能受到固定监控、控制接口和背景 GC 的较大相对影响，不能视为纯 render CPU 时间。

1. 压测器对照：每框架同一暖机进程依次运行 `(4 workers,1/128 抽样)`、`(8,1/128)`、`(4,不抽样)`，然后反序重复；每窗 12 秒，共 36 窗。
2. 监控对照：每框架四个新进程按 lean/off/off/lean 顺序运行，每窗 15 秒，均先暖机 8 秒，共 24 窗。
3. 完整矩阵：3 页面 × 3 延迟 × 3 并发（1、16、64）× 6 框架 × 2 轮，共 324 窗，每窗 8 秒。每个新进程先暖机 8 秒，每个测试单元额外暖机 2 秒。第二轮反转框架顺序；单元顺序使用固定随机种子 20260922 和 20260923。
4. 大页、50 ms、并发 64 的重点复核：每框架 3 个新进程，每窗 30 秒，先暖机 30 秒；轮次轮换框架顺序，共 18 窗。

重点复核的暖机最初计划为 8 秒。在监控预实验发现新进程之间有明显波动后，**任何正式矩阵/重点窗口开始前**统一将重点复核暖机延长到 30 秒；完整矩阵与开销对照仍保持原来的 8 秒启动暖机。决定、时间和当时已有的监控对照数据保存在 `evidence/warmup-amendment.json`。延长暖机也不能保证消除了所有 JIT/GC 差异，仍需阅读重复范围。

合计 402 个测量窗口，暖机单独运行且不进入统计。短矩阵用于覆盖场景，重点场景用三次较长窗口评估重复性；不能把这些短时实验当成长时间稳定性或内存泄漏测试。完整矩阵仅两次重复，不提供稳健的置信区间；p99 尤其在并发 1、500 ms 的短窗中样本很少，必须结合样本数阅读。

每轮矩阵中，同一框架在一个进程内连续完成全部单元，因此某个小页窗口的 RSS 可能保留此前大页留下的内存高水位，不代表小页独立启动时的内存占用。所有框架使用相同单元顺序以平衡此影响；主表的大页重点复核另外使用新进程。

## 监控开销

同一监控模块预加载到所有应用。lean 模式使用 20 ms 分辨率的事件循环直方图、GC PerformanceObserver（只累计次数、时长、最大值和类型）、每秒一次 `process.memoryUsage()`；不在应用内定时读文件、不添加逐请求中间件、不记录逐请求日志。记录内存采样函数自身耗时。

off 模式关闭事件循环直方图、GC observer 和定时内存采样；仅在窗口边界获取 CPU、ELU 和内存。因此 off 并不等于完全零监控，但保留相同的控制接口和边界操作。对照用来估计周期性监控增量；新进程/JIT/GC 差异仍可能影响结果，不把几百分点的单次差异直接当作因果收益。

cgroup 的 CPU 限流、内存和 OOM 事件只在窗口前后由外部辅助进程读取。辅助 Node 显式清空 `NODE_OPTIONS`，不会重复加载监控。cgroup 差值包含窗口周边辅助操作，主要用于资源上限检查；应用 CPU 主指标采用应用自身 `process.cpuUsage()`，不把边界辅助进程算成 SSR 进程 CPU。

## 压测器开销与边界

正式矩阵和重点复核最多使用 4 个 worker（并发 1 时只启动 1 个，其他并发为 4 个），HTTP/1.1 keep-alive，闭环固定并发，无 TLS、代理或压缩。每个 data chunk 只累计字节，不做 UTF-8 转换、Buffer 合并或内容扫描。所有响应检查状态、字节区间、ETag 和 Content-Encoding；完整内容在压测前独立验收，窗口还需通过后端调用数一一对应的检查。

压测器在线字节边界使用验收范围的 ±1.5% 以避免控制过程因微小格式变化提前中断；最终分析更加严格：逐窗口响应字节数的最小值和最大值，都必须与同框架、同页面、同延迟的独立验收值精确相等，否则汇总脚本拒绝出报告。因此最终“通过”不只依赖在线的宽容差。

初始客户端对照的参考条件是每个 worker 每 128 个请求抽样合并 Buffer，检查请求标识及结束标志。36 个客户端对照完成后，无抽样条件的 RPS 中位数高出参考条件约 2%–12.5%。短窗/JIT/GC 状态也可能造成该差异，不能把它直接认定为抽样的因果开销；为进一步减少这项干扰，在**第一个正式矩阵窗口开始前**，对六框架统一决定使用 `sampleEvery=0`。决策时间和当时全部客户端对照结果保存在 `evidence/protocol-amendment.json`，不根据正式排名选择性修改配置。监控对照的两种模式继续使用相同 1/128 抽样，因此该对照只回答其固定客户端配置下的监控增量，不能给正式数据推导精确补偿系数。

闭环并发会限制可观测吞吐：忽略所有计算和传输，理想上限已经是 `并发数 / 后端等待秒数`，例如并发 64、后端 500 ms 时最多约 128 RPS。因此高延迟组 RPS 接近，并不证明框架的计算能力相同；本报告同时给出 CPU ms/请求，并用后端 50 ms 的大页场景观察较强计算压力。

延迟在响应 `end` 时记录；在使用抽样的对照窗里，内容校验在其后进行，但仍可能延迟下一次发压。吞吐计时起点为所有 worker 最早开始发请求，终点为最后请求完成；包含收尾在途请求时间，不使用名义秒数直接作分母。应用监控快照早于分位数排序和结果 JSON 写盘，避免把报告整理算入 SSR 处理时间。

每个测量窗口启动新的压测器进程与 HTTP agent，窗口内复用 keep-alive 连接，但最初的 DNS/TCP 建连仍计入请求耗时。暖机主要针对 SSR 进程及其后端连接池，不代表正式窗口沿用了压测器的旧连接。所有框架采用相同方式。

增加到 8 个 worker 的对照仍保持总 CPU 配额 4，检验 worker 分配开销，不能单独证明网络、内核和压测器绝不构成瓶颈。必须同时检查压测器 CPU、各 worker ELU、后端等待、请求完整性与重复结果。默认不做网络出口/宿主机公网压测。

## 指标的准确含义

- **RPS/QPS**：本报告 RPS = 校验成功的完整 HTML 响应数 / 实际发压到收尾秒数；QPS 若指本次页面 HTTP 请求，则与 RPS 同义，不是数据库 QPS。记录错误及后端调用数，不能将错误响应算进有效吞吐。
- **p50/p95/p99**：单个请求从发起到完整 HTML 收完的时长，包含后端等待、JSON 传输/解析、排队、SSR、hydration 数据序列化、响应传输及客户端调度。分位数采用排序后的 nearest rank。
- **firstBodyMs**：收到第一个响应 body chunk 的时间，不等同于浏览器 TTFB 或完整页面可用。流式框架可能很早输出外壳，主排名使用完整响应。
- **CPU%**：一个逻辑 CPU 满载记为 100%，多线程可超过 100%；不是占整个宿主机百分比。CPU ms/request 以进程 CPU 总耗时除成功请求数。
- **ELU**：Node 主事件循环利用率，与 CPU% 不是同一个指标。
- **event-loop delay**：原始 `monitorEventLoopDelay` 值。分辨率 20 ms 下，空闲值也常接近 20 ms；不能把原始 p95=20 ms 写成“阻塞了 20 ms”。
- **GC**：Node 观察到的 GC 事件次数、时长与类型。累计时长比例不是精确的 stop-the-world 占比，也不是 GC CPU 占比；观察器不能替代 CPU profile。
- **内存**：RSS/heap/external 的每秒采样最大值及窗口末值；RSS 采样峰值可能漏掉短峰。cgroup memory.peak 是容器启动以来峰值，不能冒充单窗口峰值。off 模式没有连续内存采样，不宜用其峰值直接比较 lean 模式。

框架原生 JSON/hydration 序列化和 HTML 渲染已包含在整体请求与 CPU 指标中。本轮没有对所有框架内部阶段做等价插桩，**不单独报告“纯序列化耗时”或“纯 render 耗时”**。总延迟减去设定后端延迟仍包含多种开销，尤其不能用两个总体 p95 相减推导阶段 p95。

## 复现与销毁

在具备 Docker 和 Python 3 的机器上依次执行 `reproduce/setup.py`、`reproduce/validate.py`、`reproduce/run.py`。先检查当前无同标签的运行资源；脚本检测到已有资源或结果会拒绝覆盖。具体 Node 镜像、依赖锁、生成器、负载器、补丁和验收代码随报告保留。

`run.py` 完成或出错均按 `ssrbench.run=20260922-v2` 标签销毁本轮容器、网络和数据卷。原始指标、验收结果、配置和可复现生成代码留存；生成的应用、node_modules、JSON fixture 和服务随临时数据卷销毁。清理只针对本轮资源，不运行全局 prune，也不删除用户其他镜像或容器。

正式测量前曾修复一次辅助采样进程继承 `NODE_OPTIONS`、重复监听监控端口的问题；当时尚无测量窗口产出，环境已清理后重建并重新验收。失败日志及清理回执保存在 `preflight-failure.log`、`evidence/preflight-run-failure.txt` 和 `evidence/preflight-cleanup.json`，不混入框架请求错误率。
